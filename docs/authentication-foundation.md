# Authentication foundation (Task 008A)

- Better Auth 1.7.7 owns `User`, `Session`, `Account`, `Verification`, and `TwoFactor`; Prisma maps these to `auth_*` tables. Framework-generated string IDs and UTC timestamps are retained.
- The existing server-only Prisma singleton supplies the PostgreSQL adapter. Task 008C mounts a minimal authentication HTTP handler; no login UI or privileged admin endpoints exist.
- Email/password authentication is configured with public signup disabled. No users or admin accounts are provisioned.
- TOTP enrollment requires verification; MFA secrets and backup codes are encrypted with `BETTER_AUTH_SECRET`. The local secret is random and Git-ignored; deployed secrets must be separate and stable.
- `BETTER_AUTH_URL` sets the explicit trusted origin. HTTPS is required outside local development, with secure cookies for HTTPS.
- Plugin support alone does not enforce mandatory admin MFA or application authorization. Privileged endpoints remain unavailable until session-level MFA enforcement, recovery policy, and security tests are complete. This foundation is not production-ready admin authentication.
- Application admin memberships reference Better Auth `User.id`; optional customer profile links remain deferred. Authentication alone never grants an admin role. Guest customer profiles need no auth identity; phone matches never prove ownership or authorize order-history access.
- The blueprint's proposed custom account/session/MFA storage must not duplicate Better Auth-owned tables. Future profile links must preserve business history with restrictive foreign keys; framework-only session/account/2FA rows currently cascade on identity deletion. No user-deletion workflow is exposed.
- Identity images are optional URL references, not stored image bytes. No OAuth providers, email delivery, or registration workflow are implemented here.

Only OWNER has settings, admin-membership, and audit permissions. These permission names do not implement those business modules.

No caller-supplied override exists; no privileged HTTP routes are exposed.
- Before granting any privileged access, integrate and test trusted MFA completion tied to the exact Better Auth session, with expiry, revocation, recovery/reset, and trusted-device handling. The identity HTTP handler added in 008C does not open privileged endpoints. Role-policy checks alone never authorize a request.

### Proof storage and remaining authorization integration

1. Implemented in 008E: optional date `session.additionalFields.mfaVerifiedAt`, `input: false`, `returned: false`, default null, on the existing framework Session table. `databaseHooks.session.create.before` resets it to null on every creation, including copied/rotated sessions.
2. Implemented in 008E: an application plugin after `twoFactor` captures a live, signed, database-backed login challenge only when no authenticated session exists and the factor was already verified. A successful TOTP handler must consume that challenge and set the exact `ctx.context.newSession`. Enrollment and existing-session TOTP never qualify. API errors, client flags, response tokens, and enrollment flags alone never establish proof.
3. Implemented in 008E: persist the server timestamp only to that matching, newly created, unexpired Session ID/User ID/token in PostgreSQL, with null prior proof and current matching factor/enrollment checks. Failure grants no proof. Storage and the restricted login-proof writer were implemented in 008E. Task 008F integrates authorization with a bounded proof age and disables factor-management flows until coordinated revocation exists; the future revocation controls above remain prerequisites for exposing those flows.

## Verified session lifecycle (Task 008D)

Primary authority: the locally installed **Better Auth 1.7.7** implementation, including `dist/api/routes/sign-in.mjs` and the source paths above. Live checks invoked the existing HTTP handler against local PostgreSQL; no configuration or authorization overrides were used.

- Before enrollment, correct credentials create usable password-only sessions. Enrollment requires an authenticated session and the correct credential password; the factor remains unverified and `twoFactorEnabled` remains false until valid TOTP.
- Successful enrollment replaces only the enrolling session. Another pre-enrollment password-only session remains usable and subsequently reports `twoFactorEnabled: true`. This is a verified counterexample to enrollment flags as session proof.
- With MFA enabled, credential sign-in briefly creates a database session inside the framework, then the 2FA after hook deletes it before returning a challenge. The caller receives no usable session before TOTP; invalid TOTP grants none. Valid TOTP consumes the challenge and creates a usable session; replay cannot create another.
- Valid TOTP on an already authenticated, enrolled session retains its ID and leaves its database row unchanged. Neither persisted session fields nor `getSession` distinguishes that session from one never verified with TOTP.
- **Version-specific enrollment behavior:** its successful JSON response contains the revoked old token, while Set-Cookie and `ctx.context.newSession` reference the replacement session. Any future proof hook must use authoritative framework session context, never the response token.
- MFA disable/recovery paths and trusted-device creation/reuse remain blocked by existing configuration. Source inspection shows native MFA disable rotates only the current session rather than revoking every session; exposing it would require additional revocation controls.
- Old password-only and newly TOTP-verified fixture sessions all fail current admin authorization because they have no membership. The separate session-MFA gate still always denies privilege; no admin account or privileged route was created.

**Minimum recommendation:** use the framework Session additional field and trusted successful-TOTP hook described above. Unmodified 1.7.7 cannot provide the required persisted session-bound assurance. This is a private extension of Better Auth's own session model, not a parallel proof-token/session system. A successful sign-in, enrollment flag, cookie, or session creation timestamp alone is insufficient. Keep privilege blocked until the additive field, revocation/serialization controls, and lifecycle tests are separately approved and implemented.

Verification: `node --conditions=react-server --import tsx scripts/verify-mfa-lifecycle.ts` — **16 passed, 0 failed, 0 skipped**. One random local non-admin identity was removed in `finally`, along with its framework children/challenges. All 11 table fingerprints and counts matched their starting values: five categories, four roles, zero admin memberships and no authentication records. The script stops before writes if authentication records already exist because native verification lookup can clean expired verification rows globally.

Still required before production: MFA freshness policy, controlled recovery/reset and credential-change workflows, trusted-device prohibition, race-safe revocation, and shared production rate-limit storage. No schema/migration or runtime implementation changed in 008D.

## Complete local onboarding (Task 008H)

Commands are prepared for **later authorized operator use**, from this project root. No real identity was provisioned, enrolled, or activated during this task.

| Operation | Explicit command suffix on `node --conditions=react-server --import tsx scripts/bootstrap-owner.ts` |
| --- | --- |
| Read-only empty-bootstrap check | `--check` |
| Create a new inactive Owner; refuses any existing Owner | `--create` |
| Resume the single intended inactive Owner and verify enrollment | `--enroll` |
| New credential/TOTP login, identity confirmation, atomic activation | `--activate` |

- Enrollment/activation require an interactive local terminal and the intended email/current password. Credentials, TOTP codes, and cookies stay in process memory; none are command arguments, environment inputs, files, or terminal reports. These operations never create/merge accounts. Public signup/enrollment remain disabled; the local capability cannot originate from HTTP claims.
- `--enroll` displays only the enrollment URI in a private Windows Forms window via `local-owner-secret-view.ts`. It uses a static PowerShell program and an anonymous stdin pipe, suppresses child stdout/stderr, and performs no network, browser, QR-service, disk, or automatic clipboard transfer. The window clears/disposes its content and closes after two minutes. It then requires a hidden TOTP code. Backup/recovery codes are not delivered. Enrollment verification leaves membership inactive and cannot write credential-login MFA proof.
- An interrupted unverified factor is resumed through the installed framework's password-protected `getTOTPURI` only under the local capability. The identity must still be the sole inactive/non-disabled Owner, with exactly one unverified factor, MFA disabled, and a live matching password-only session. No factor or credential is replaced. Verified/active/ambiguous states refuse secret retrieval; completed enrollment proceeds through a separate activation login. Wrong credentials leave the factor/account unchanged.
- `--activate` requires a fresh credential-login TOTP challenge, private proof at most five minutes old, and the exact current session. The operator confirms `ACTIVATE VERIFIED OWNER`. Under the global local-operator lock and per-Owner lifecycle lock, activation rechecks the sole pending Owner/no competing active Owner, locks the retained session row, deletes other sessions and pending challenges/known attempt records, and enables only that membership in one database transaction. Failure rolls back activation and revocation together. Concurrent activations have one winner.
- The proof writer shares the lifecycle lock. An active OWNER cannot obtain proof from a challenge issued at/before the membership activation boundary (`AdminUser.updatedAt`). Thus verification that consumed a challenge before activation but creates its session afterward fails, deletes its unproven session, and returns a sanitized error. Proof written before activation is either the retained exact session or revoked. A new post-activation credential/TOTP login remains supported.
- The operator CLI signs out its session and removes its own pending challenge/attempt records on exit. An interrupted process may leave inactive enrollment or an expiring challenge; it cannot silently activate or replace a factor. If activation committed before a process interruption, rerunning activation refuses the already active membership. No automatic rollback of verified factors, recovery, MFA disabling, or trusted-device bypass exists.

Checks cover a real paused verification crossing activation, concurrent activation, competing Owner conflict, non-Owner denial, revoked-cookie denial, and unchanged credentials/factors on interrupted resume. Only a temporary fixture Owner was activated and removed.
- TypeScript, ESLint, production build, and whitespace checks passed. Windows Forms availability and non-interactive viewer refusal were verified. **Human visual/URI-entry acceptance of the private window was not run**; no test secret was displayed to a human. Review that local presentation before real onboarding. Freshness policies remain conservative defaults (five-minute activation, twelve-hour admin proof).
